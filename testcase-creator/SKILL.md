# Test Case Creator

## Output contract

- **One business feature per file**: `<output-dir>/<feature-slug>.md` using the [template](templates/testcase.md). Do not combine multiple features in one file or split FE and BE into separate files. Each file has **Frontend and Backend sections**. If a side does not exist (API-only, UI-only), write `N/A — <evidence-based reason>`; do not invent cases. Put cross-feature flows in the file of the initiating feature and link related features to avoid duplication.
- Every case has a stable ID `TC-<FEATURE>-FE-001` / `TC-<FEATURE>-BE-001`, one independently verifiable objective, sources/traceability, test type/level, priority/risk, setup and starting data, reproducible actions, observable/measurable expected results, and cleanup/safety where relevant. BE cases verify both response **and** side effects in DB/cache/queue/log (including `no change`); FE cases verify UI and interaction, not use a hidden button as proof of API authorization.
- Keep **design/readiness** separate from **execution outcome**. A case with missing specification is `pending-spec`, not runnable; a blocked environment is `blocked`; `failed` means an actual run diverged from an approved oracle. Never infer pass/fail from readiness. Do not invent status codes, errors, thresholds, copy, or business rules. Record the question, owner, and source needed. Use N/A only when the surface genuinely does not exist, with evidence/reason.
- Do not promise to cover “all possible” scenarios: that set is unbounded. Build model-based, risk-prioritized coverage; explicitly record selection method, assumptions, exclusions and residual risks. Critical/high risks and required rules need explicit cases; use combinatorial coverage only where justified. See [test design techniques](references/test-design-techniques.md).

## Workflow

0. **Confirm the testcase file's display language before drafting or writing it.** Ask the user: “Which language should the testcase file use for its display text: English or Vietnamese?” If the user already specified the language for this file, do not ask again. Apply the choice consistently to titles, section headings, descriptions, steps, expected results, questions, and notes. Keep IDs, API names, schema fields, error codes, and other literal system values unchanged; preserve exact UI copy in the language required by the specification. Do not translate technical identifiers or alter their meaning.
1. Read [QA model and expected-result rules](references/source-map.md), then the references relevant to the feature's surfaces. The skill contains the checklists needed to work independently; it does not depend on an external documentation service. Do not treat examples as rules for the feature under test.
2. Inspect approved specification/acceptance criteria, design version, API contract, role/action/ownership matrix, BR/E/EC registers, NFRs, architecture/data-flow, code/schema and recent changes when available. Enumerate entry points, screens, endpoints, actors/tenants, data states, dependencies, configuration/feature flags, persistence and side-effect boundaries. For a large/multi-team system, first follow [large-project operations](references/large-projects.md) to map feature/service ownership, shared suites, release traceability, supported variants and environment strategy. Ask concise questions when missing information determines expected results; a transparent draft may still be produced.
3. Model the feature and apply techniques from [test design](references/test-design-techniques.md): equivalence partitions, boundary values, decision tables, state transitions, use-case paths, risk-based error guessing, and pairwise/higher-strength combinations when suitable. Cover input (absent/null/empty/whitespace, types, bounds, Unicode, malicious), actor/resource/tenant, state/transition, sequence/time, concurrency, dependency failures and volume. Give known interactions (e.g. permission × tenant × ownership; commit × timeout × retry) explicit cases rather than assuming pairwise covers them. Record risk rationale, selection strength, exclusions, and untested paths. Never claim literal exhaustive coverage.
4. Populate FE using the [component library](references/frontend-components.md) and [additional FE surfaces](references/frontend-extended.md). Consider access → title/design/default → each element (Default/Validation/Event) → state/flow → accessibility/responsive/compatibility. Link common checks instead of copying the entire library; add feature-specific values and errors.
5. Populate BE using [API/auth/validation/errors](references/backend-api.md) and [data/async/operations](references/backend-systems.md). Include direct API requests that bypass the UI. Verify side effects for successful and failed paths. API-only features still get an FE N/A section. Use [NFR & integration](references/nonfunctional-integration.md) for cross-layer testing and measurable performance/security/operations criteria; do not conflate API latency with screen transition time.
6. Copy `templates/testcase.md` **for each feature** to the requested output directory (if unspecified, ask or use an existing testcase directory in the project; if none exists, use `./docs/testcases/` and state that choice). Populate properties with real values, searchable tags and concrete source links; no placeholders in an approved suite. Render human-readable content in the language confirmed in Step 0; keep YAML keys, controlled values, IDs and technical identifiers stable. Keep case IDs stable. `Design status`/readiness is `ready` only when source, preconditions/setup/data, steps, oracle, and relevant cleanup/safety are adequate; otherwise use `pending-spec` or `blocked` and record why. Do not mark cases approved just because they are ready. `Coverage` lists groups/requirements considered and justified N/A groups.
7. Review coverage bidirectionally: requirements→cases and cases→source; inspect decision tables/state transitions, test data, environment, success/failure/partial-failure, rare paths, cross-tenant permissions, rollback/idempotency, NFR thresholds, and cleanup. For release scope, perform change-impact analysis and trace selected/excluded regression cases across suites. Report denominator/method, risks/exclusions, owners, and design-readiness counts. Do not claim complete with important gaps.
8. For execution, create a **separate run record** linked by stable case ID; record release/build/environment, tester/date, execution result, actual result, redacted evidence, and defect ID. In large projects, maintain release-level requirement→feature→case→run traceability and canonical ownership of shared suites. Follow [execution governance](references/execution-governance.md). Do not alter expected results to match implementation without owner approval. Do not run penetration, load, destructive or fault-injection tests against production without explicit authorization.
