# Pull Request Delivery

PR invocation requests a summary comment plus line-specific detail comments by default; honor explicit draft/read-only requests. Permission covers review comments, confirmation replies and resolution of verified-fixed finding threads on re-review; and approval when the conditions below are met; not merging, unrelated thread resolution or code edits.

1. Resolve the exact host/repository/PR from the URL or unambiguous context; ask if ambiguous. Read the PR target/base and pin base/head SHAs. Review all cumulative branch changes from merge-base(base, head) → head using the complete PR diff across every file page. Do not substitute the latest commit diff or only changes since the previous review; the head SHA identifies the snapshot/anchors, not the review scope. Read previous review summary/threads for [round and finding status](review-history.md).
2. Prepare the shared template: round/time, counts, Resolved and Problems lists. Include the reviewed commit in inline comment metadata; place material evidence/limitations in the relevant Detail rather than adding report sections. For each current problem, prepare Detail with `Lý do`, `Đề xuất chỉnh sửa`, `🧪 Cách kiểm tra` (specific check plus expected result). Omit `File` when the inline anchor provides the location. Add `🔁 Tái hiện` only when needed; never imply proposed checks already passed; put its stable ID and severity in the inline comment title. On re-review, apply [confirmation rules](review-history.md#pr-re-review-confirmation): reply with current fix evidence, resolve only verified-fixed finding threads and verify state; link confirmations from Resolved. Keep OPEN/UNVERIFIED threads unresolved.
3. Recheck head before publishing. If changed, reassess affected source, counts and anchors. If freshness cannot be checked, disclose the reviewed SHA; never pretend an anchor was verified for the current head.
4. Post each Detail as an inline review comment on the exact file, side and line/range supported by the PR diff and provider API, tied to the reviewed commit. Use current head lines for additions/context, base side for deletions when supported. For a document PR, anchor to its changed source lines. Reuse/link a matching existing inline discussion for an unchanged prior issue; do not duplicate it. Do not submit an approval or platform request-changes action just to publish comments.
5. Post one summary comment for this round, linking each Problem to its verified inline comment/thread. The summary has no Detail heading or detail content; Problems links directly to inline comments. If a finding cannot be anchored (outside diff, non-line-addressable document, unavailable inline tool), mark its detail as unposted in Problems with a short reason and return the unposted detail in chat; do not insert it into the PR summary. Never attach to an unrelated line. If there are no Problems, finish required confirmation replies/thread resolutions, then apply the approval rules below; use the summary as the approval review body when eligible instead of duplicating it in another comment.
6. Prefer an authenticated connector supporting inline PR comments plus conversation comments; otherwise use an authenticated CLI/API with explicit repository/PR. For multiline CLI bodies, use a temporary file and `--body-file` where supported; never interpolate report text into shell commands. Verify returned/read-back body, commit/side/line, PR target and URLs before claiming publication. Return the summary URL and brief outcome.

On timeout/uncertain writes, read existing summary/inline comments for the same round, finding IDs and snapshot before retrying. Continue only missing writes. Do not replace/delete previous comments. If some details posted but summary failed, return their actual URLs and the missing summary inline; clearly report partial delivery. Authentication/network/authorization failures require full unposted content inline with target PR/SHA and reason; no invented comment links or local-file substitute. A local copy is optional only when requested. A patch without a resolved PR identity is local review.

## Approve when no issues remain

PR review invocation includes submitting `APPROVE` when the actual review has zero Problems (no OPEN or UNVERIFIED findings), adequate coverage/evidence for the full cumulative diff and no material verification gaps. This applies to first reviews and re-reviews. Honor explicit draft/read-only/no-approve instructions. Simulated resolutions, assumed fixes, a resolved thread or zero counts alone never establish eligibility.

Immediately recheck the PR is open, ready for review and its head SHA matches the reviewed snapshot. If head changed, reassess affected changes before approving. Missing runtime checks do not automatically block approval if static evidence is adequate for the change; disclose material limits honestly. Never claim checks passed when they were not run.

Use an authenticated approval tool/API with action `APPROVE`, the reviewed head SHA and the normal summary body (no Detail section). On success, read back the review state `APPROVED`, actor, commit and PR URL before reporting approval. After uncertain writes, inspect existing reviews before retrying. If an eligible approval already exists for this actor/head, avoid submitting duplicates. Approval does not authorize merging or bypassing branch protection.

When Problems remain or evidence is materially incomplete, publish a `COMMENT` summary and keep the relevant issues open; do not approve or automatically submit platform `REQUEST_CHANGES`. If GitHub rejects approval (for example, self-review of the author's own PR or insufficient permission), publish the review result as a comment and state why approval could not be submitted. Do not switch accounts or impersonate another reviewer to bypass the restriction.
